# RC TV Launcher: setup, local companion and recovery design

Research date: 2 November 2026. Scope: repository inspection and published platform research only. No builds, installs, device connections, ADB commands, configuration changes or source-code edits were performed. This report is the only added artifact.

**Decision:** extend the existing Compose setup, preferences, keyboard, pairing and native remote. Add durable setup/recovery state and a TV-hosted HTTPS companion page. Use Android Home selection first. Offer native-phone-assisted shell operations only on devices with an explicitly authorised working ADB transport and a separately verified recovery route. Do not ship automatic Xiaomi package takeover until that recovery gate passes.

The existing Xiaomi installation is a successful documented takeover, not proof that every Xiaomi can be safely converted or recovered without a PC. Preserve it unchanged.

Evidence labels used throughout:

- **[Repository]** inspected implementation or historical device results recorded in this repository; historical results were not repeated in this task.
- **[API]** documented platform support; availability and OEM behaviour can still vary.
- **[Design]** selected implementation contract, not existing functionality.
- **[Hardware gate]** a specific acceptance check required before enabling the relevant feature, not a request for another general research pass.

## 2. Technical feasibility and selected activation methods

| Method | Authority, versions and user action | OEM/reboot/recovery implications | Selection |
| --- | --- | --- | --- |
| A. HOME role / normal chooser | [API] RoleManager HOME is API 29+. Check availability, request using system consent, then inspect state. No privileged permission required | Firmware can expose the role while another Home still wins. Preferences can persist without effective physical Home routing. Return through the same chooser when stock is enabled | Default strategy; supported across this app's API 30+ range only when capability checks and actual routing pass |
| B. Android Settings intents | [API] HOME_SETTINGS, SETTINGS, APPLICATION_DETAILS_SETTINGS, ACCESSIBILITY_SETTINGS and INPUT_METHOD_SETTINGS; use the input-method picker for selection. Launch exported system handlers, catch absence/security errors, give exact menu fallback | Opens UI; grants nothing and cannot restore a disabled package by itself. Back usually returns through the activity stack, but OEM task behaviour must be tested | Always provide button-led settings assistance; no repeated chooser loop after proven failure |
| C. Ordinary on-device command execution | [API] A child process retains RC TV's UID. Calling `pm` from the app does not confer shell privileges. Changing other packages' enabled state requires protected authority | Runtime permission prompts cannot grant this authority. Root or hidden permission tricks are outside scope | Reject as an activation mechanism |
| D. TV-local authorised ADB client | [Design] Possible only if adbd already exposes a compatible local endpoint and accepts the client after system authorisation. Implement explicit short-lived shell session, not a public shell server | Same-device connection, authorisation prompt handling and reboot reconnection are firmware dependent. It cannot switch on an inaccessible ADB transport by wishing it available | Optional later adapter; not the primary Android 11 solution |
| E1. Native phone to existing TCP ADB | [API + Design] Android phone can run an ADB host implementation. TV needs an enabled reachable authenticated endpoint and approval of this phone's own ADB key | Xiaomi's recorded PC connection at port 5555 is evidence of a listener on that installation, not evidence that a fresh box enables it identically. PC authorisation does not authorise the phone. Reboot/network changes require reconnect and possibly renewed authorisation | Selected advanced assistance where independently demonstrated; no arbitrary shell UI |
| E2. Modern wireless ADB pairing | [API] Documented Android wireless-pairing baseline is phone 11+, **TV/Wear 13+**; use actual pairing screen and connection endpoint | Pairing and connection ports differ and may change. Firmware can omit the feature. Do not infer it from TV API 30 | Use on capable future TVs; do not present Android-11-phone instructions as supported on these boxes |
| E3. Android phone USB host to TV ADB | [API] Phone USB host APIs plus USB-device permission and TV RSA authorisation; TV must expose a real USB device-mode ADB interface | A TV USB-A port may be host-only. A cable alone proves nothing; do not suggest unsafe host-to-host wiring. Wired Xiaomi rescue remains unverified | Conditional alternative after exact hardware/cable validation |
| F. Other legitimate approaches | Managed-device Home policy requires properly provisioned device/profile-owner authority; OEM supported default-Home APIs require an actual vendor contract. Accessibility can redirect Home on some firmware | Enterprise provisioning is inappropriate for an existing personal TV and may require reset. Accessibility redirection does not establish boot/default Home and is reversible only while its controls remain accessible | No consumer device-owner provisioning. Preserve optional existing Home gestures, clearly labelled separately; no boot-loop launcher relaunch service |

[API sources: RoleManager](https://developer.android.com/reference/android/app/role/RoleManager), [Settings actions](https://developer.android.com/reference/android/provider/Settings), [Android 11 protected component-state permission](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android11-release/core/res/AndroidManifest.xml), [managed Home policy](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#addPersistentPreferredActivity(android.content.ComponentName,%20android.content.IntentFilter,%20android.content.ComponentName)), [USB host](https://developer.android.com/develop/connectivity/usb/host).

The documented legacy TCP workflow first uses an existing USB ADB connection to enable TCP mode. A vendor may expose TCP debugging directly, but that is a separate capability to verify. If there is no Home chooser that works, no authorised network listener and no usable USB ADB device interface, neither RC TV nor a phone can create shell authority through a QR code. The supported fallback is RC TV as a normal app, or one authorised computer-assisted provisioning session where a supported transport exists. If no supported transport exists at all, retain app mode. [Android ADB transport and authorisation documentation](https://developer.android.com/tools/adb).

**Xiaomi decision [Repository + Design]:** do not retry standard Home selection as a cure for the already diagnosed firmware-774 priority behaviour. Repository evidence records Google Home priority 2, setupwraith RecoveryActivity 1 and RC TV 0 before takeover. Android restricts positive Home intent priorities for nonprivileged apps; editing RC TV's manifest priority is not a maintainable fix. The exact OEM routing explanation remains an inference, while the resulting two-package takeover is a documented outcome. [Intent-filter priority rules](https://developer.android.com/guide/topics/manifest/intent-filter-element#priority).

**Can the known takeover be automated without a PC?** Technically yes, conditionally: an authorised native phone ADB client can issue the same allowlisted shell operations. Product-safe automation is **not yet established**, because an independent recovery path has not been demonstrated. No new installation may disable stock packages until that gate passes. The existing working Xiaomi is recognised and explained, never automatically reconfigured.

## 3. Selected architecture and durable contracts

Use one shared Compose wizard shell, backed by small deterministic controllers. Keep platform and privileged transport outside UI components.

| Module [Design] | Responsibility and integration |
| --- | --- |
| `DeviceCapabilityRepository` | Snapshot SDK, build fingerprint, active user, RAM/low-RAM status, Home candidates including disabled ones, role state, resolved Home, exported settings targets, network addresses, accessibility/IME state and optional transport evidence. Extend HomeIntegration and SystemSettings. Distinguish unknown/inaccessible from absent |
| `SetupCoordinator` | Versioned step IDs; allowed transitions; enabled feature requirements; durable resume; Return from Settings rechecks. Replace numerical automatic-step logic without replacing working preference setters |
| `HomeStrategyRegistry` | `StandardRole`, `HomeSettings`, `AssistedAdb` and `AppOnly`; optional future `LocalAdb`. Rank by observed capability, not brand. Known-firmware profiles may restrict an operation, never grant authority |
| `RecoveryCoordinator` | Reads the activation journal; generates explicit restoration plan; verifies stock availability and actual Home; prevents RC uninstall/disable before verification |
| `CompanionRuntime` | Existing TLS native adapter plus new HTTPS/browser adapter; share command validation, approval/revocation authority and runtime lifetime. Separate remote, download and privileged-operation capabilities |
| `AdbOperationRunner` on phone | Session-scoped, explicit user actions; fixed typed operations; its own Keystore-protected ADB identity. Never export ADB private keys, accept shell text from TV/web or open a phone shell proxy |
| `VerificationRepository` | Timestamped observations and evidence level: requested, selected, resolved, physical Home confirmed, reboot confirmed. No boolean conflating all five |

Persist setup in a small dedicated DataStore: schema version, current step ID, per-step state (`not_started`, `incomplete`, `checking`, `verified`, `skipped`, `unsupported`, `failed`), selected features, last settings destination and verification evidence. Write the checkpoint **before** leaving for Android Settings. Persist validated preference changes immediately through existing Preferences. On restart/reboot, open the saved step and refresh capabilities; discard stale “checking” states and ephemeral approval secrets. Back returns to the previous wizard page; “Finish later” pauses, does not declare success. Rerun creates a fresh verification session using current choices, never defaults them.

Keep a separate atomic, versioned recovery journal with a last-known-good copy: device/user identity, strategy, selected original Home component(s), exact baseline package/component overrides, baseline role versus resolved Home, plan version/hash, confirmed consent, intended changes, per-operation readback and verification status. Capture it before any mutation and copy a nonsecret rescue version to the authorised phone. Bind operations to the precise TV, user, build and fresh snapshot; never execute an imported journal on a different device. Missing history means “activation method unknown”, not guessed restoration.

For the existing Xiaomi, import the documented firmware-774 baseline only after matching all relevant identifiers and obtaining a live read-only snapshot in a future implementation session. Mark its provenance as historical; do not pretend current disabled states are the original baseline.

Do not store new recovery journals only in the launcher DataStore that currently resets on corruption. Do not include them automatically in portable appearance backups. A rescue record is instructions and state, not shell authority.

**Performance:** reuse FocusButton, typography and wallpaper caches. Show one preview/backdrop, lazy app lists and low-motion defaults on low-RAM devices. Run probes off the UI thread, cancel on exit, avoid periodic package scans. Keep bounded workers, streams and timeouts; stream APKs from disk/assets. The download listener exists only while its page is open or an active bounded download completes. Browser/native remote survives leaving Home only if the existing separately consented accessibility lifetime supports it. No additional always-on service or boot receiver is needed for wizard persistence.

### 3A. Professional Settings UX: mandatory implementation architecture

This requirement applies to Settings, initial setup and recovery. It preserves RC TV's Cinematic Glass identity and all functional settings and stored preferences. The existing Xiaomi Home configuration must remain unchanged throughout Settings development: no package-state, Home-role, preferred-activity, Home-gesture, Accessibility, boot or debugging changes as a side effect of UI work. Test activation/recovery mutation paths on separate designated hardware, not the preserved working Xiaomi.

**Reference and evidence [API/product evidence]:** Projectivy's official release notes describe labelled settings icons, aspect-correct preview panels, contextual permission indicators, accessibility fixes and remote-navigation refinements. Use those as usability references for discoverability, context and feedback. This report does not claim a hands-on audit of its latest UI or copy its exact layout. RC's two-panel design below is a selected design, not an assertion that every Projectivy screen has that layout. [Projectivy official releases](https://github.com/spocky/miproja1/releases).

**Existing foundation [Repository]:** `ui/SettingsHub.kt` already defines seven categories and return-target helpers; `ui/CinematicLauncher.kt` assembles their controls. `docs/SETTINGS-ORGANISATION.md` documents the previous navigation-only reorganisation, including legacy `launcher`/`power` route aliases. Reuse this structure, `FocusButton`, `AppearanceTokens`, `LauncherTypography`, `SystemSettingsLink` and the existing domain callbacks. The present UI is a category list followed by a separate subpage, not a persistent two-panel shell.

#### Two-panel shell and precise remote behaviour [Design]

- Left rail occupies roughly 28–32% of usable width with icon, category name and restrained selection indicator. Right panel contains title, current values and grouped rows. Keep one stable backdrop and readable glass scrim; avoid transparent text over uncontrolled wallpaper contrast. Use a full-screen picker/wizard for images, reordering, typing tests and recovery confirmation when two panels would reduce usability.
- Initial Settings entry focuses the last visited category, restoring its content/scroll state. Up/Down in the rail changes highlighted category and shows its right-panel content without a click or data mutation. Right/OK enters the last focused visible enabled row, first actionable row on first visit. Left from a nonediting row returns to the active category. Up/Down within content follows stable row order, does not jump into the rail, and stops at boundaries rather than wrapping on a held key.
- Back closes the topmost chooser/dialog/editor first, then nested workspace, then content to category rail, then Settings to the original Home/utility entry. Physical Back and visible Back use one navigation reducer. In a value editor, Left/Right operate the control; Back leaves the editor and restores its row rather than unexpectedly switching category. Text input receives editing keys before shell navigation.
- Store focus by stable category/entry ID plus scroll anchor, not row index. Returning from Android Settings restores the launching row and refreshes its status on resume. Removed/unavailable rows fall back to the nearest visible enabled sibling. Utility routes retain origin; system settings cannot guarantee an OEM Back stack, so durable state still resumes correctly on reopen.
- Most settings use a single full-width row: icon, label, optional concise subtitle, current value and status/chevron. OK opens a bounded choice sheet or toggles a clearly labelled switch. Long-OK must not be required for standard Settings functions. Long descriptions live in an accessible details region; primary actions stay visible.
- Common choices remain directly visible. ## 5. Restore Original Launcher wizard and safety model

Entry: **Settings → System & Recovery → Restore Original Launcher**. Keep a separate lightweight recovery entry activity, reachable from the system app list and authenticated phone where Android permits, with minimal dependencies on the cinematic UI. This improves crash isolation, but does not rescue a missing, disabled or completely broken RC TV package.

1. **Check this TV.** Identify current user, original launcher, enabled state, activation strategy and journal confidence. Buttons: **Continue**, **Open Android Settings**, **Back**. If ambiguous, show all credible Home candidates with labels/components and require selection; never call FallbackHome, a chooser or setup/recovery activity a working original launcher.
2. **Review restoration.** Explain the precise changes, preserved preferences and available rescue route. Buttons: **Restore original Home**, **Cancel**. Remote-control pairing alone cannot authorise package changes; require a fresh physical TV confirmation or explicit local phone recovery confirmation when RC cannot run, plus Android ADB authorisation.
3. **Remove Home redirection.** Detect both RC Home-gesture and remote-accessibility state. Buttons: **Open Home-gesture settings**, **Open Accessibility**, **Check again**. Turn off RC's internal interception mode through a supported own-service control after consent; guide Android service disablement if needed. Do not disable unrelated accessibility services. Record unfinished changes. This is separate from changing Android Home.
4. **Restore availability.** Standard route: **Open original app details**, **Open Home settings**; allow user to Enable in Android if the firmware exposes it. Assisted route: **Connect Android phone**, **Authorise connection**, **Restore packages**. Execute only the approved device-specific plan. Stop on failure and preserve both launchers wherever possible.
5. **Select original Home.** **Open Home selection**, or an authorised shell selection where standard UI cannot do it. Deliberately select the original component, then read back. A baseline journal that named RC as role holder is not a reason to leave RC selected during “Restore Original Launcher”.
6. **Test original Home.** **Open original launcher**, **Test physical Home**, **Retry**, **Open Android Settings**. An explicit launch alone is only a smoke test. Require enabled/launchable stock, Home resolution and actual physical Home behaviour with interception off. User confirms the stock screen; authorised shell inspection may corroborate foreground state. Do not reboot until Home and Settings work. Track a subsequent normal reboot separately.
7. **Restored.** **Keep RC TV installed** (default), **Export settings**, **Uninstall RC TV…** only after verified restoration. Before uninstall, disclose that Android removes private RC data and imported wallpaper files; provide an off-device settings backup and separate image export if preserving those assets is desired. Uninstall is optional and system-confirmed. Switching itself never clears preferences, favourites, wallpapers, approvals or existing backups.

### Xiaomi firmware 774 restoration specifics

[Repository] The documented rollback restores Google TV **before** setupwraith, with enable followed by restoring DEFAULT (0) for each. Preserve the exact recorded baseline; ENABLED (1) and DEFAULT (0) are not interchangeable. Do not change individual component overrides that were never changed by takeover.

[Design] The runner must: verify identities/user and expected states; restore `com.google.android.apps.tv.launcherx`; confirm it is launchable; restore `com.google.android.tungsten.setupwraith`; then verify the resulting candidate set, select/test the original Google Home, and check Android Settings/network. The older prepared procedure restores a historical role baseline naming RC TV; that is a diagnostic rollback baseline, not the final outcome of this consumer “original Home” flow. Stop if any necessary package is absent, not merely disabled.

This ordering is grounded in the repository record. **Post-takeover restoration has not been recorded as executed successfully.** It is a hardware acceptance gate before shipping the one-button path.

### Recovery outside the happy path

| Failure | Supported response [Design] |
| --- | --- |
| Debugging disabled | Use physical remote to Android Settings and user-visible Enable/Home controls, if demonstrated. A phone cannot silently re-enable debugging. If those controls are absent, stop; restoration requires a supported authorised transport |
| Reboot loses ADB | Existing paired remote approval and ADB authorisation are different. Reconnect only to an actual available endpoint; otherwise use physical Settings or validated USB rescue. Do not assume an automatic watchdog survives |
| IP/router/Wi-Fi changes | Rebind/re-discover remote, compare pinned identity, reconnect TV network with physical settings. Rescue phone retains instructions, not a guaranteed connection. Do not depend on old IPs |
| RC cinematic UI crashes | Try the lightweight recovery activity or independent system Settings route; phone ADB can operate directly only when transport and authorisation still work |
| RC package cannot open and network/debugging unavailable | Only a physically demonstrated independent OEM Settings/Enable route or validated wired rescue qualifies. The current Xiaomi has no established guarantee for this combination. Do not newly disable stock packages under that condition |
| Interrupted restoration | Read actual states on resume; do not replay completed steps blindly. Prefer leaving stock enabled and RC intact. Do not undo a successful stock restoration just because a later optional step failed |
| Factory reset | Outside data-preserving restoration; manufacturer-specific last resort with explicit data-loss disclosure, never the wizard's promised safety net |

**Independent recovery gate:** before disabling any stock package, demonstrate a rescue route that still works with debugging unavailable and RC unable to start, on that firmware. A shortcut from RC to Android Settings does not meet this test. A live ADB connection plus a rollback script does not meet it either. If the gate fails, advanced takeover stays unavailable; preserve normal app/chooser use.

## 6. TV-hosted local phone companion

### Selected local distribution and browser transport

All page assets and the optional native APK are served **by the TV**. No GitHub, public website, cloud account, public download host, CDN scripts or external fonts are part of the primary experience.

The browser needs a new HTTPS endpoint; retain the current native protocol for compatibility. Use a small maintained HTTP implementation with bounded parsing and a same-origin JSON command API over HTTPS. Start with request/response and short status polling while visible; WebSocket is unnecessary for the current button/text command volume. Adapt both transports into the same pairing/command authority, but use distinct credential audiences so native tokens cannot accidentally authorise browser or privileged endpoints.

**Trust constraint [API + Repository]:** LocalIdentity currently produces a self-signed Keystore certificate, without a browser-trusted hostname/IP certificate. A QR fingerprint is useful to a native client but ordinary browser JavaScript cannot override TLS verification or pin the connection's certificate. Serving a PIN/token through HTTP does not fix active interception: injected JavaScript could steal it. Browser warnings and exceptions are real browser behaviour, not solved by encryption inside an unauthenticated page. [Google's local HTTPS guidance](https://web.dev/articles/how-to-use-local-https), [Mozilla certificate-error guidance](https://support.mozilla.org/en-US/kb/error-codes-secure-websites).

**Selected fully local solution [Design]:** use a separate browser-suitable per-TV HTTPS identity with proper server usage and SANs for the advertised local address/name. Support only browser combinations where the user can inspect the actual certificate SHA-256 fingerprint, compare it to the physical TV, and accept a site-specific exception. Show the certificate/address instructions on the TV **before** opening the page. Never say simply “ignore warnings”, install a general-purpose root CA, or ship one shared private key in every APK. An in-page “fingerprint” is not authentication of the page that displays it.

After that explicit trust step, browser pairing and remote work locally. On address/certificate changes re-establish trust; never silently fall back to HTTP commands. If a browser cannot inspect/accept the required certificate, mark browser remote unsupported there and offer the locally served existing native Android app. This is an honest compatibility boundary: a warning-free, universally compatible, offline browser-only first visit is not delivered by the current trust model. Public certificate provisioning could change that trade-off later, but is not a dependency of this selected design.

### Exact connection experience

1. TV: **Settings → Phone Companion → Connect phone**. Start the bounded local HTTPS/download session; show network name where accessible, readable address, QR, session expiry, **New QR**, **Connection help**, **Stop serving**.
2. QR contains a local HTTPS URL and short-lived session locator, never a permanent remote token, ADB key, shell command or authority grant. Keep bootstrap material out of query logs/referrers. Manual address plus displayed code is the fallback.
3. Phone: establish certificate trust as above, then page offers **Use browser remote**, **Use keyboard**, **Download Android companion**, **Connection help**. Labels state requirements before installation.
4. Enter the two-minute pairing code. TV displays claimed phone name plus a matching session identifier/code, with **Allow this phone** and **Reject**, Cancel/Reject focused by default. Phone name is untrusted text. Pending request expires after one minute. Approval is local and scoped to remote control.
5. Establish a high-entropy, revocable credential and renewable short session. Browser uses Secure/HttpOnly/SameSite=Strict cookies plus request-origin and CSRF protection; state changes are POST-only. No credentials in localStorage, URLs, analytics or logs. Commands retain sequence and replay controls. Do not send/retain password text. On a changed origin/IP, require browser re-pairing rather than copying cookies through URLs.
6. Browser D-pad/OK/Back/Home/search route to existing policy. Other-app control/typing require the same separate TV opt-in/Accessibility/IME gates as native; browser pairing cannot bypass them. Clear typed buffers on send/disconnect; protect password and installer/permission screens. Treat accepted dispatch as different from confirmed third-party app behaviour.
7. TV: **Paired devices** shows type, user label, last connection and scope; **Revoke**, **Revoke all…**, **Stop remote**, **Stop sharing downloads** are separate actions. Revocation immediately invalidates all relevant leases and sessions. Keep the current maximum of three devices initially and make replacing a device explicit.

TLS and HTTP protections: LAN-interface-only binding; same-subnet policy retained initially; no router changes; validate Host against current endpoints, Origin and session audience to resist DNS rebinding/cross-site attacks; strict CSP, no CORS wildcard, no inline untrusted HTML, no third-party assets. Use reviewed server/parser components rather than a hand-written HTTP parser. Preserve bounded workers/body/header sizes/timeouts and rate limits; APK streams have a separate download allowance so they do not block remote commands. No public filesystem listing or arbitrary file route.

### Secure bundled APK delivery

Bundle a release-signed `za.co.rc.tv.phone` APK as a fixed TV asset, plus a build-generated manifest of version, minSdk, bytes, SHA-256 and signer identity. A future packaging check must reject stale/wrong-package/debug artifacts for consumer distribution. Keep signer continuity for existing users or explicitly resolve the current development-signature migration; do not solve signature mismatch by uninstalling and losing credentials.

Serve only that known immutable file, streaming with correct APK MIME type, Content-Length, Content-Disposition and bounded/range handling. The page shows version/size/checksum, Android-only compatibility, and the TV shows the trusted digest independently. A checksum served alongside an APK over unauthenticated HTTP is not proof of authenticity. Initial sideload trust comes from the verified HTTPS connection and independent TV comparison; Android signatures protect update continuity, not the identity of an arbitrary first-install download.

Phone downloads through its browser/download app and follows Android's per-source unknown-app installation consent. Do not request TV package-install permission merely to serve bytes. A normal browser cannot silently install APKs or reliably verify package signatures itself. The Android native app may subsequently open its own relevant settings intents; the download page cannot impersonate the browser's installer authority. [Android unknown-source settings API](https://developer.android.com/reference/android/provider/Settings#ACTION_MANAGE_UNKNOWN_APP_SOURCES).

### Network and lifecycle cases

| Condition | UI and implementation response |
| --- | --- |
| No LAN address | Show **Open network settings**, **Retry**; no QR to an invented address. Internet is unnecessary when local connectivity works |
| Phone on mobile data, guest network or isolated Wi-Fi | Explain same reachable LAN, disable VPN only if user chooses, reconnect to main network; never suggest opening router ports or exposing ADB globally |
| QR unreadable/unsupported | Enlarge QR, high contrast, readable URL/code; manual entry. Camera permission belongs to phone's chosen scanner, not the TV |
| Multicast blocked | Manual address works if unicast is allowed; browser does not depend on NSD. Native NSD remains optional |
| Network/address changes | Watch network and link-property changes; close old listeners/leases, rebind, refresh QR and address. Retain native approvals but validate pinned identity. Browser re-trust/re-pair may be necessary |

Future native targets must account for Android's local-network protection: official guidance requires the runtime permission or supported system-mediated picker path for apps targeting API 37+. Current projects target API 36. Add denial/retry UX when upgrading, rather than requesting unrelated location/media permissions for LAN access. [Android local-network permission](https://developer.android.com/privacy-and-security/local-network-permission).

## 7. Phone-assisted switching and device compatibility

An ordinary phone webpage supports HTTPS remote/keyboard and instructions through the TV server. It cannot directly speak the existing raw TLS protocol or open arbitrary TCP ADB sockets. Browser WebUSB exists on some platforms but needs secure context, USB permission and suitable hardware; it is not a general same-Wi-Fi TV activation solution. Direct Sockets is a restricted Isolated Web App capability, not ordinary mobile webpage support. **Extend the existing native Android companion for advanced ADB work; do not build a second phone app.** [Chrome Direct Sockets](https://developer.chrome.com/docs/iwa/direct-sockets), [WebUSB requirements](https://developer.chrome.com/docs/capabilities/usb).

Native assistance screens [Design]: **Choose TV → Choose connection method → Open TV developer settings instructions → Authorise on TV → Check recovery readiness → Review exact change → Activate/Restore → Verify → Save rescue instructions → Disconnect**. Large single-purpose buttons, explicit progress/error, Retry and Cancel. PC-free means no typed commands for the owner; the app still explains that Android is authorising advanced device changes.

Keep ADB authority entirely outside the TV HTTP/native remote API. The phone talks directly to the TV's existing authorised adbd, with strict endpoint/identity/user verification, and executes a finite plan. No `exec(command)` endpoint, URL-supplied package, arbitrary intent, LAN scan or automatic transport enabling. New phone authorisation shows Android's RSA prompt. Legacy TCP ADB does not provide modern TLS transport confidentiality; restrict use to a trusted private network, keep the session brief, and offer user-led debugging shutdown/revocation only after a debugging-independent recovery route is proven.

Each operation is a transaction with baseline/precondition, fresh consent, mutation, bounded readback, then next stage. Before any disabling: verify stable RC launch, settings, backup, original packages, network ownership risks and independent recovery. On known Xiaomi, setupwraith disablement can affect owned networks: its active-network ownership must be checked through authorised diagnostics, not inferred from SSID/model. If ownership cannot be established or requires user-led network migration, stop that plan. Do not automate forgetting Wi-Fi. A disconnected runner cannot roll back; show exact remaining rescue actions and never promise guaranteed automatic rollback after loss of authority.

| Local distribution | Internet disconnected but same LAN active: QR/readable address, local page and exact bundled APK work. Wrong certificate/hash refuses continuation; unsupported browser gets truthful fallback |
| Pairing abuse | Bad/expired PIN, pending timeout, denied TV prompt, fourth device, replay, revoked token, cross-transport token, repeated request and stale QR all rejected |
| Browser security | Cross-site POST, missing/wrong Origin, malicious Host/DNS rebinding, CSRF, XSS labels and oversized requests rejected; no unauthenticated command or shell route |
| Input | Benign text reaches supported selected editor only; password/installer/permission UI cannot be typed/approved remotely; text is not persisted/logged |
| Network/lifecycle | DHCP change, Wi-Fi/Ethernet switch, multicast filtering, AP isolation, mobile data, VPN, sleep and server stop have accurate states; no stale sockets/leases or hidden endless polling |
| ADB assistance | Wrong TV/user/build, unauthorised/revoked host key, disabled debugging, changed port and interrupted authorisation stop safely. Phone has a separate ADB key; remote pairing never grants shell access |
| Backup/uninstall | Settings export validates/readbacks; images separately preserved if uninstall selected; no uninstall option until successful stock verification; backup imports never change Android authority |
| KD5 memory/performance | Measure against current build on exact hardware: no sustained listener/bitmap duplication, no ANR/OOM, responsive repeated D-pad presses; proposed acceptance budget is ≤20 MiB additional steady-state PSS with companion idle and ≤100 ms p95 button feedback, validated rather than assumed |
| Regressions | Native pinning, durable pairing/revocation, existing wallpaper/favourites/backup tests and physical remote continue working; no privilege changes merely from upgrade |

## 10. Remaining blockers and firm product boundaries

1. **Independent Xiaomi rescue is not established.** Current documentation does not prove offline Enable controls independent of RC, or usable wired ADB. This blocks shipping new stock-package takeover under the requested safety requirements; it does not negate the existing successful installation.
2. **Android 11 ADB bootstrap is device-specific.** Xiaomi's existing TCP listener is recorded; fresh-phone authorisation and persistence need explicit hardware acceptance. KD5 transport/chooser behaviour is unverified. Without a reachable authorised transport, software cannot automate privileged switching. A supported computer bootstrap is the fallback where possible; app mode otherwise.
3. **Local browser trust adds a real first-visit step.** The selected certificate-comparison path requires browser support and user action; it cannot honestly promise universal warning-free QR pairing. The locally served native Android client is the stronger pinned alternative and is required for the selected advanced ADB experience.
4. **Stock restoration after the known takeover needs execution acceptance.** Guidance and command-order tests exist; a successful actual restore is not recorded. Also distinguish restoring the old role baseline from selecting the original Home as the user's final goal.
5. **External preservation is limited today.** Existing settings backups omit image files and system state; the Xiaomi external-document/HDD flow is not established. Do not offer data-preserving uninstall until required assets have a verified export destination. TV Downloads alone is not protection against reset/device loss.

Everything else above is an implementation work package with a selected solution. No further general research pass is needed. The consumer promise should be: button-driven setup, locally hosted phone connection, truthful Home status and reversible switching on validated devices, with app mode retained wherever firmware cannot safely support takeover.
